Продолжаем разработку тестового задания M-Social «Вкусная осень».

Предыдущие этапы завершены:

- анализ требований;
- фиксация архитектуры и допущений;
- проектирование PostgreSQL-модели.

На этом этапе впервые разрешено создавать код и инфраструктуру.

Цель текущего этапа — создать минимальный рабочий skeleton приложения, который станет основой дальнейшей реализации.

НЕ реализуй пока:

- Telegram Bot API;
- Telegram polling;
- LLM integration;
- bot decision logic;
- support ticket business logic;
- operator panel;
- statistics;
- evaluation harness.

Сейчас нужен только корректный Laravel/PostgreSQL/Docker foundation.

Перед началом полностью перечитай:

- `AGENTS.md`
- `docs/task.md`
- `docs/architecture.md`
- `docs/assumptions.md`
- `docs/database-schema.md`

Не меняй утверждённую архитектуру без необходимости.

Не подключай дополнительные Laravel packages, если они не требуются текущему этапу.

В частности, пока НЕ подключай:

- Laravel AI SDK;

# 3. Laravel skeleton

Создай минимальное Laravel 13 приложение в текущем репозитории.

Сохрани стандартную структуру Laravel настолько, насколько это возможно.

Не создавай заранее сложную собственную структуру каталогов под будущие сервисы.

Не добавляй абстракции, пока для них нет реализации.

После установки убедись, что:

- `composer.json` корректен;
- `composer.lock` присутствует;
- Laravel запускается;
- стандартные тесты запускаются.

---

# 4. PostgreSQL configuration

Laravel должен быть настроен на PostgreSQL.

В `.env.example` должны присутствовать только безопасные placeholders для:

- `DB_CONNECTION=pgsql`;
- `DB_HOST`;
- `DB_PORT`;
- `DB_DATABASE`;
- `DB_USERNAME`;
- `DB_PASSWORD`.

Не добавляй реальные credentials.

PostgreSQL должен работать отдельным Docker Compose service.

Добавь healthcheck PostgreSQL.

Application container не должен стартовать миграции до готовности PostgreSQL.

---

# 5. Docker

Необходимо создать Docker setup для локального MVP.

Предпочитай минимальную конфигурацию.

Для текущего этапа достаточно сервисов:

- `app`;
- `postgres`.

Telegram worker будет добавлен позже, когда появится соответствующая Artisan command.

Не создавай неработающий placeholder worker, из-за которого `docker compose up` будет падать.

---

# 6. Application container

Создай подходящий Dockerfile для Laravel MVP.

Используй PHP 8.4.

Установи только необходимые PHP extensions для Laravel + PostgreSQL.

Не устанавливай:

- Redis extension;
- Xdebug;
- supervisor;
- Node.js;
- cron;
- nginx;

если они не нужны текущему skeleton.

Для локального тестового MVP допустимо использовать:

`php artisan serve --host=0.0.0.0 --port=8000`

Не требуется строить production nginx/php-fpm инфраструктуру.

Это должно быть явно обозначено в документации как local development/MVP transport.

Приложение должно быть доступно с host machine.

---

# 7. Docker build

Docker image должен:

1. устанавливать PHP dependencies через Composer;
2. использовать `composer.lock`;
3. не включать `.env` с секретами;
4. иметь разумный `.dockerignore`.

Не копируй в image:

- `.git`;
- `.idea`;
- локальный `.env`;
- временные файлы;
- agent logs;
- другие ненужные IDE/runtime artifacts.

При этом документы проекта должны оставаться в репозитории.

---

# 8. APP_KEY

`APP_KEY` является секретом и не должен быть закоммичен как реальное значение.

Не помещай рабочий application key в `.env.example`.

Для текущего этапа выбери простой и понятный development workflow, позволяющий получить `APP_KEY` без его хранения в git.

ВАЖНО:

не создавай сложную инфраструктуру с отдельными secret containers или distributed secret management только ради APP_KEY.

Если для первоначального setup требуется отдельный одноразовый шаг до первого `docker compose up`, это допустимо только если он:

- минимален;
- понятен;
- честно описан в README;
- после первоначального setup весь стек запускается одной командой `docker compose up`.

Если можешь безопасно сделать первичную генерацию ключа автоматически без лишней сложности — допускается такой вариант.

Объясни выбранное решение.

# 10. Environment

Подготовь `.env.example`.

Кроме стандартных Laravel-настроек должны быть предусмотрены placeholders, но пока без реализации:

```env
TELEGRAM_BOT_TOKEN=
LLM_PROVIDER=
LLM_MODEL=
LLM_API_KEY=
LLM_BASE_URL=
LLM_TIMEOUT=
```

Не добавляй реальные значения.

Если какие-то из этих переменных пока вообще не используются кодом — это нормально.

Не создавай фиктивную LLM-конфигурацию только ради того, чтобы их использовать.

---

# 11. Timezone

Не меняй глобальную timezone хранения PostgreSQL ради Москвы.

Время в БД должно оставаться абсолютным/UTC.

Подготовь Laravel config так, чтобы позднее бизнес-логика могла явно использовать:

`Europe/Moscow`.

Не размазывай вызовы timezone по коду на текущем этапе.

Если отдельная конфигурационная переменная сейчас не нужна — не добавляй её только формально.

---

# 12. Health endpoint

Добавь минимальный HTTP health endpoint.

Он должен подтверждать, что Laravel application отвечает.

Не превращай его в большую систему мониторинга.

Если Laravel 13 предоставляет подходящий штатный механизм health route — предпочти его собственной сложной реализации.

Health endpoint не должен раскрывать:

- environment variables;
- database password;
- API tokens;
- stack trace;
- другую чувствительную информацию.
