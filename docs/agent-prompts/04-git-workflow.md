# Git workflow

Работа ведётся в существующей ветке:

`task_mvp-tgbot`

На этом и последующих этапах после успешного завершения задачи необходимо самостоятельно создавать git commit.

## Перед началом работы

Обязательно выполни:

```bash
git status
git branch --show-current
git log -10 --pretty=format:"%h %s"
```

Проверь:

1. текущая ветка — строго `task_mvp-tgbot`;
2. в рабочем дереве нет изменений пользователя, которые можно случайно включить в commit;
3. стиль последних commit messages.

Если текущая ветка отличается от `task_mvp-tgbot`:

- НЕ переключай ветку самостоятельно;
- НЕ создавай commit;
- остановись и сообщи об этом.

---

## Существующие изменения пользователя

Не добавляй в commit посторонние изменения, которые существовали до текущей задачи.

Особенно внимательно относись к:

- `.idea/`;
- локальным IDE-файлам;
- пользовательским изменениям документации;
- временным файлам;
- другим незакоммиченным изменениям.

Используй выборочное добавление файлов через `git add`, а не бездумный:

```bash
git add .
```

Перед commit обязательно проверь:

```bash
git status
git diff
git diff --cached
```

В staged changes должны находиться только изменения текущего этапа.

---

## Commit message

Commit message должен быть на русском языке.

Перед созданием commit изучи предыдущие сообщения:

```bash
git log -15 --pretty=format:"%s"
```

Используй похожий стиль, структуру и уровень детализации.

Не копируй старый текст буквально.

Сообщение должно кратко описывать фактически выполненную работу текущего этапа.

Не используй в commit message упоминания:

- ChatGPT;
- Codex;
- AI;
- нейросети;
- «сгенерировано ИИ»;
- тестового промпта.

История git должна описывать изменения проекта, а не используемый инструмент разработки.

---

## Когда создавать commit

Создавай commit только после того, как:

1. реализация текущего этапа полностью завершена;
2. выполнены предусмотренные prompt проверки;
3. ошибки проверок исправлены либо явно установлено, что проверка невозможна по объективной причине;
4. просмотрен итоговый `git diff`;
5. в staged changes отсутствуют посторонние файлы.

Если тесты или критическая проверка падают из-за изменений текущего этапа — сначала исправь проблему.

Не создавай заведомо сломанный commit только ради завершения задачи.

---

## Один этап — один осмысленный commit

По умолчанию текущий этап должен завершаться одним логически цельным commit.

Не дроби небольшой этап на большое количество технических commit вида:

- «добавил файл»;
- «фикс»;
- «ещё фикс»;
- «поправил ошибку».

Если во время этапа потребовались исправления, включи их в итоговый commit после успешной проверки.

---

## После commit

После создания commit выполни:

```bash
git status
git log -1 --stat
```

Убедись, что:

- commit создан в `task_mvp-tgbot`;
- рабочее дерево не содержит случайно оставшихся изменений текущей задачи;
- в commit вошли только необходимые файлы.

В финальном отчёте укажи:

- hash созданного commit;
- его сообщение;
- какие основные файлы вошли в commit.

---

## Push

`git push` НЕ выполняй.

Отправка изменений в удалённый репозиторий выполняется только по отдельному прямому указанию пользователя.
