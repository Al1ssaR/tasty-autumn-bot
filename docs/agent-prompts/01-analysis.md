Мы начинаем разработку тестового задания M-Social.

На данном этапе НЕ ПИШИ КОД и НЕ СОЗДАВАЙ Laravel-проект.

Сначала изучи полностью:

- AGENTS.md
- docs/task.md
- docs/promo-rules.md
- docs/requests.md

Цель текущего этапа — выполнить инженерный анализ задания до начала реализации.

Не ограничивайся пересказом ТЗ.

Нужно:

1. Выделить все функциональные требования:
    - Telegram-бот;
    - работа с LLM;
    - правила принятия решения answer/escalate;
    - обращения оператору;
    - история переписки;
    - отправка ответа оператора обратно в Telegram;
    - закрытие обращения;
    - статистика;
    - прогон тестовых обращений.

2. Выделить нефункциональные требования:
    - Laravel/PHP;
    - PostgreSQL;
    - Docker Compose;
    - запуск одной командой;
    - работа с secrets;
    - воспроизводимость;
    - тестируемость;
    - документация.

3. Найти все места, где постановка неоднозначна или неполна.

Для каждого такого места сформируй таблицу:

| Вопрос | Почему он важен | Нужно спросить менеджера или можно принять допущение | Предлагаемое решение |

Не придумывай вопросы ради количества.

Выдели только те неопределённости, которые действительно влияют на архитектуру, поведение пользователя или проверку задания.

4. Проанализируй все 25 сообщений из `docs/requests.md`.

Пока НЕ пиши финальные ответы бота.

Для каждого сообщения классифицируй ожидаемый сценарий:

- ANSWER_FROM_RULES
- ESCALATE_PARTICIPANT_DATA
- ESCALATE_MISSING_RULE
- SECURITY_OR_PROMPT_INJECTION

Если для одного сообщения возможна спорная классификация — отдельно объясни почему.

5. Проверь правила акции на потенциально сложные случаи:
    - даты;
    - относительные даты;
    - количество шансов;
    - лимиты;
    - налоги;
    - повторная регистрация чека;
    - получение призов;
    - вопросы, где правила дают только частичный ответ.

6. Отдельно проанализируй обращения №24 и №25 как security cases.

Опиши, какие гарантии должны обеспечиваться не только prompt-инструкцией, но и кодом приложения.

7. Предложи 2–3 возможных варианта архитектуры LLM-части.

Минимум сравни:

A. Передавать полный документ правил модели.
B. Искать релевантные фрагменты правил приложением и передавать их модели.
C. RAG/vector search — только если считаешь его оправданным.

Для каждого варианта укажи:

- сложность;
- надёжность;
- вероятность hallucination;
- воспроизводимость;
- соответствие масштабу данного MVP.

После сравнения предложи один вариант, но пока его не реализуй.

8. Предложи принцип обработки результата LLM.

Особенно оцени вариант структурированного результата вида:

{
"action": "answer|escalate",
"answer": "...",
"reason": "...",
"rule_references": []
}

Определи, какие проверки должны выполняться приложением после ответа модели.

9. Определи, какие данные потребуется хранить для выполнения требований операторской панели и статистики.

Пока не проектируй окончательную SQL-схему — перечисли только необходимые бизнес-сущности и связи между ними.

10. Проанализируй вопрос времени.

Правила используют МСК, а в тестовых сообщениях присутствуют относительные формулировки вроде «следующий розыгрыш».

Предложи способ:
- работы времени в production;
- получения текущего времени LLM;
- воспроизводимого тестового прогона.

11. Составь предварительный список технических рисков проекта.

Например:
- Telegram API недоступен;
- LLM API недоступен;
- LLM возвращает malformed response;
- LLM отвечает не по правилам;
- повторное Telegram update;
- ошибка отправки ответа оператора;
- пользователь пишет несколько сообщений подряд;
- утечка secret или персональных данных.

Не ограничивайся этим списком.

12. В конце сформируй:

### A. Recommended MVP scope

Что именно должно войти в тестовое задание.

### B. Out of scope

Что сознательно не стоит делать для данного MVP.

### C. Questions for project manager

Только действительно важные вопросы.

### D. Assumptions we can safely make ourselves

Допущения, которые разумнее записать в README, чем беспокоить ими менеджера.

### E. Recommended implementation stages

Разбей последующую разработку на небольшие этапы, каждый из которых можно реализовать и проверить отдельно.

ВАЖНО:

- сейчас никаких изменений файлов;
- никакого Laravel-кода;
- никаких миграций;
- никаких Dockerfile;
- никаких пакетов.

Нужен только подробный инженерный анализ.

При анализе всегда ссылайся на конкретное требование или конкретный пункт исходных материалов, когда это возможно.
