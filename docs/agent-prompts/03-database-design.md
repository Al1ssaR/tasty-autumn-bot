# Цель

Спроектировать минимальную, но достаточную PostgreSQL-модель для требований MVP:

- Telegram participant;
- история сообщений;
- решение бота/LLM;
- support ticket;
- оператор;
- Telegram delivery state;
- статистика;
- Telegram idempotency.

Схема должна быть понятной, нормализованной и объяснимой на техническом интервью.

Не проектируй универсальную CRM.

# 1. Telegram participant

Нужно спроектировать сущность, представляющую Telegram-пользователя/чат.

Учитывай принцип data minimization.

Определи, какие Telegram identifiers действительно необходимо хранить для:

- поиска участника;
- отправки ему ответа;
- связи с сообщениями;
- связи с support tickets.

Не считай Telegram-пользователя подтверждённым участником сайта акции.

Не добавляй поля профиля Telegram только потому, что Telegram API их предоставляет.

---

# 2. Messages

`messages` должны быть единой историей коммуникации.

В таблице должны помещаться:

- сообщение участника;
- автоматический ответ бота;
- системное уведомление об эскалации;
- ответ оператора.

Не создавай отдельные таблицы для каждого вида сообщений.

Спроектируй способ явно определить автора/тип сообщения.

Нужно поддержать:

- связь с participant;
- необязательную связь с support ticket;
- необязательную связь с operator;
- оригинальный текст;
- Telegram update identifier для входящего сообщения;
- Telegram message identifier при необходимости;
- delivery state исходящих сообщений;
- время успешной доставки;
- безопасное описание ошибки;
- количество попыток доставки, если это действительно нужно;
- timestamps.

Подумай, какое значение delivery state должно быть у входящих сообщений, чтобы модель не была двусмысленной.

---

# 3. Telegram idempotency

Отдельной таблицы Telegram updates нет.

Нужно обеспечить окончательную защиту от повторной обработки одного Telegram update через constraint БД.

Спроектируй:

- какое поле используется;
- nullable ли оно;
- какой UNIQUE constraint/index нужен;
- почему constraint должен быть защитой даже при наличии предварительной application-level проверки.

Учти PostgreSQL semantics для UNIQUE + NULL.

---

# 4. Bot decisions

Для каждого нового входящего сообщения, которое действительно прошло классификацию, необходимо сохранить решение.

Один классифицируемый incoming message не должен иметь несколько активных решений.

Минимально необходимо восстановить:

- `answer` или `escalate`;
- бизнес-причину;
- ссылки на правила;
- был ли результат LLM валиден;
- использован ли fail-safe;
- provider/model, если они известны;
- prompt version;
- rules version/hash;
- момент принятия решения.

ВАЖНО:

не смешивай в одно поле два разных понятия:

### Business classification

Например:

- `grounded_in_rules`;
- `participant_data_required`;
- `missing_rule`;
- `insufficient_context`;
- `unsafe_request`.

### Technical processing outcome

Например:

- LLM ответил корректно;
- malformed response;
- timeout;
- HTTP/API failure;
- application fail-safe.

Предложи чистую модель, позволяющую отличить:

`LLM решила эскалировать вопрос`

от

`приложение эскалировало вопрос, потому что LLM не сработала`.

Не создавай для этого лишнюю таблицу.

Также реши, нужно ли хранить подготовленный LLM answer внутри decision, если пользовательский ответ одновременно хранится как `message`.

Избегай бессмысленного дублирования, но учитывай аудит и evaluation.

---

# 5. Support tickets

Support ticket должен обеспечивать:

- связь с participant;
- связь с сообщением, которое вызвало эскалацию;
- состояние `open/closed`;
- причину эскалации;
- время создания;
- момент первого ответа оператора;
- момент закрытия.

У участника в MVP может существовать максимум ОДИН открытый ticket.

Это требование должно обеспечиваться не только application logic, но по возможности и PostgreSQL constraint/index.

Рассмотри partial unique index PostgreSQL и оцени, подходит ли он здесь.

Последующие сообщения пользователя при открытом ticket добавляются к нему и не создают новый ticket.

---

# 6. Operator / users

Для операторской панели используется Laravel session authentication.

Сложного RBAC нет.

Реши, нужна ли вообще отдельная колонка `role`, если все пользователи этой MVP-панели являются операторами.

Не добавляй роли/permissions только ради формальной архитектуры.

Ответ оператора должен позволять определить его автора.

---

# 7. Связи

Отдельно опиши cardinality и ownership:

- participant → messages;
- participant → support tickets;
- incoming message → bot decision;
- ticket → messages;
- operator → operator messages;
- trigger message → support ticket.

Проверь, где связь должна быть:

- `NOT NULL`;
- nullable;
- unique.

Избегай циклической модели, требующей неудобной последовательности INSERT без реальной необходимости.

---

# 8. Delete/update behaviour

Для каждого foreign key обоснуй поведение:

- RESTRICT;
- CASCADE;
- SET NULL.

Не применяй CASCADE автоматически.

Учитывай, что история поддержки является важной частью MVP.

Например, удаление operator account не должно случайно уничтожить историю сообщений.

---

# 9. Типы данных PostgreSQL

Обоснуй выбор основных типов:

- BIGINT / BIGSERIAL;
- VARCHAR/TEXT;
- TIMESTAMP WITH TIME ZONE;
- JSONB;
- integer;
- boolean.

Отдельно оцени способы хранения состояний:

A. PostgreSQL ENUM;
B. VARCHAR + CHECK constraint.

Выбери один подход для данного MVP и объясни решение с учётом Laravel migrations и дальнейшего изменения состояний.

Не используй boolean там, где существует больше двух бизнес-состояний.

Для каждого индекса объясни, какой запрос он обслуживает.

# 11. Статистика

Проверь, что предложенная схема позволяет вычислить без отдельных счётчиков:

### bot resolved

Количество incoming messages, для которых:

- decision = `answer`;
- решение валидно;
- автоматический ответ успешно доставлен.

### escalated

Количество созданных support tickets.

### average operator response time

Среднее:

`first_operator_response_at - support_ticket.created_at`

только для tickets, где `first_operator_response_at IS NOT NULL`.

Не создавай таблицу статистики.

Покажи пример концептуального SQL или псевдо-SQL для каждой метрики.

Это нужно только для проверки проектируемости схемы, не как production implementation.

---

# 12. Concurrency

Отдельно проверь две race conditions:

### Duplicate Telegram update

Два процесса одновременно получают один update.

### Duplicate open ticket

Два сообщения одного participant почти одновременно приводят к escalation.

Покажи, какие database constraints делают состояние корректным независимо от application-level предварительных проверок.

Не проектируй distributed locking infrastructure.

Не сохраняй redacted и unredacted копию одного текста в разных таблицах без убедительной причины.

# 16. Самопроверка

После проектирования выполни мысленную проверку схемы минимум на следующих сценариях:

### Scenario A

Новый пользователь задаёт обычный вопрос → LLM отвечает → ответ успешно доставляется.

### Scenario B

Новый пользователь задаёт персональный вопрос → создаётся ticket.

### Scenario C

Тот же пользователь пишет ещё одно сообщение при открытом ticket.

### Scenario D

Оператор отвечает → Telegram delivery успешна.

### Scenario E

Оператор отвечает → Telegram delivery failed.

### Scenario F

Один Telegram update приходит повторно.

### Scenario G

Два сообщения одновременно пытаются создать два open tickets одного participant.

### Scenario H

LLM timeout → application fail-safe escalation.

Проверь, что для каждого сценария понятно:

- какие строки создаются;
- какие связи используются;
- какие constraints защищают данные;
- можно ли после этого корректно вычислить статистику.
