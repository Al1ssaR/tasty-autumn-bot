## Принятые решения

Следующие решения считаются утверждёнными и не требуют повторного обсуждения.

### Общая архитектура

Используем Laravel-монолит.

В одном приложении находятся:

- Telegram bot worker;
- web-панель операторов;
- application/business logic;
- интеграция с LLM;
- интеграция с Telegram;
- работа с PostgreSQL.

Микросервисы для данного MVP не нужны.

---

### Telegram

Для локального MVP используем long polling.

Причина:

- проект должен запускаться через `docker compose up`;
- не требуется публичный HTTPS endpoint;
- не требуется ngrok или другой внешний tunnel;
- такой режим проще воспроизводится проверяющим.

Webhook можно указать как production improvement.

Поддерживаем только текстовые сообщения.

Фото, документы, voice, sticker и другие типы сообщений находятся вне scope MVP.

---

### LLM

Для MVP передаём модели полный текст `docs/promo-rules.md`.

Vector database, embeddings и RAG не используем.

Причина: документ правил небольшой, полностью помещается в контекст, а retrieval добавляет лишнюю сложность и риск пропуска связанных правил.

LLM:

- не имеет tools;
- не имеет доступа к БД;
- не имеет доступа к Telegram API;
- не имеет административных возможностей;
- не выполняет никаких операций с чеками, участниками, победителями или призами.

LLM используется только для анализа пользовательского сообщения и формирования структурированного решения.

---

### Контракт LLM

Архитектурно предполагаем результат:

- `action`: `answer` или `escalate`;
- `reason`: enum;
- `answer`: текст;
- `rule_references`: список пунктов правил.

Предварительный enum причин:

- `grounded_in_rules`;
- `participant_data_required`;
- `missing_rule`;
- `insufficient_context`;
- `unsafe_request`.

Окончательная JSON Schema будет разработана на этапе реализации LLM.

При malformed response, timeout или другой ошибке LLM применяется fail-safe:

`escalate`.

---

### Security cases

Не создавай regex или hardcoded проверки специально под тексты тестовых обращений №24 и №25.

Защита должна быть архитектурной, а не подогнанной под evaluation dataset.

Если LLM классифицирует запрос как `unsafe_request`, приложение НЕ должно отправлять пользователю свободно сгенерированный security-ответ модели.

Приложение должно использовать собственный статический безопасный ответ.

При этом основная гарантия безопасности:

- у модели отсутствуют административные инструменты;
- приложение принимает только разрешённый закрытый набор действий;
- заявления пользователя о роли сотрудника/администратора не дают никаких прав.

---

### Работа с персональными данными

Перед отправкой пользовательского текста в LLM необходимо предусмотреть маскирование очевидных чувствительных значений, в частности:

- номера банковской карты;
- номера телефона, когда он указан непосредственно в сообщении.

Исходный текст при этом может быть необходим оператору и храниться как часть обращения.

Диагностические application logs не должны содержать полный пользовательский payload с такими значениями.

Конкретную реализацию redaction спроектируем позже.

---

### Работа с открытым обращением

При первом `escalate` создаётся support ticket.

Если пользователь отправляет последующие сообщения, пока у него есть открытое обращение:

- новое сообщение добавляется в историю существующего обращения;
- новый ticket не создаётся;
- сообщение не считается новым самостоятельно закрытым ботом вопросом;
- автоматический LLM-ответ для него не требуется;
- сообщение ожидает оператора.

После закрытия обращения новое сообщение снова проходит обычную классификацию.

Это является допущением MVP.

---

### Частичный ответ при эскалации

Если часть составного вопроса достоверно покрывается правилами, но другая часть требует оператора:

- итоговое действие всё равно `escalate`;
- допускается сообщить пользователю достоверную общую информацию;
- затем приложение обязательно добавляет сообщение о передаче оператору;
- такое сообщение не считается «закрытым ботом».

Это является допущением MVP.

---

### Статистика

Для MVP:

`bot resolved`:
одно входящее сообщение, для которого было принято валидное решение `answer` и автоматический ответ успешно отправлен пользователю.

`escalated`:
количество созданных support tickets.

Последующие сообщения внутри уже открытого ticket не увеличивают число эскалаций.

`average operator response time`:
среднее время между `support_ticket.created_at` и первым сохранённым ответом оператора.

Учитываются только tickets, на которые оператор уже ответил.

Статистика all-time.

Фильтр по периоду находится вне scope MVP.

---

### Доставка Telegram

Для MVP не создаём отдельную сущность `telegram_delivery_attempt`.

Состояние доставки исходящего сообщения хранится непосредственно у `message`.

Предусмотреть концептуально:

- delivery status;
- Telegram message id;
- время успешной отправки;
- безопасное описание ошибки;
- количество попыток при необходимости.

Конкретные поля будут утверждены при проектировании БД.

---

### Telegram idempotency

Для MVP не создаём отдельную таблицу Telegram updates.

Идемпотентность обеспечиваем хранением `telegram_update_id` или другого подходящего Telegram identifier у входящего сообщения и UNIQUE constraint.

Точное поле нужно определить на этапе проектирования БД.

---

### Очередь

Redis, RabbitMQ и другие брокеры не используем.

Laravel database queue также пока не добавляем.

Для MVP отправка Telegram может выполняться синхронно.

Если во время реализации появится техническая необходимость в очереди, сначала обоснуй её, а не добавляй автоматически.

---

### Время

PostgreSQL timestamps храним в UTC.

Бизнес-timezone:

`Europe/Moscow`.

Текущее время не должно неявно браться моделью из собственных знаний.

Приложение передаёт модели текущее время.

Для evaluation-прогона используем frozen clock:

`2026-09-30T12:00:00+03:00`

Это значение должно быть задокументировано.

---

### Operator panel

Для MVP:

- общая очередь обращений;
- без assignment;
- без SLA;
- без сложного RBAC.

Панель не должна быть публично доступна без авторизации.

Используем обычную серверную session-based авторизацию Laravel.

Достаточно роли/пользователя оператора.

Конкретная реализация авторизации будет выбрана позже.

### 2. Создай `docs/architecture.md`

Документ должен объяснять архитектуру проекта разработчику и проверяющему тестовое.

Какую задачу решает система.

Опиши:

- Telegram bot worker;
- Laravel web application;
- message processing/orchestration;
- LLM client;
- Telegram client;

- PostgreSQL.

Пошагово:

Telegram → application → redaction → LLM → validation → persistence → Telegram.

Telegram → application → LLM decision → ticket → notification → operator panel.

Operator panel → persistence → Telegram API → delivery state.

Покажи, чему модель может и не может доверять.

Подчеркни, что LLM не является агентом с административными возможностями.

### LLM provider

Конкретный LLM-провайдер и модель пока не утверждены.

Архитектура должна позволять заменить провайдера без изменения основной бизнес-логики.

На текущем этапе:
- использовать абстракцию LLM client;
- конфигурацию провайдера/модели предусмотреть через environment;
- не добавлять SDK конкретного провайдера;
- не фиксировать конкретную модель в архитектуре как обязательную.

Выбор будет сделан перед этапом реализации LLM-интеграции после уточнения доступного API.

#### Failure strategy

Опиши поведение при:

- LLM timeout;
- LLM malformed output;
- Telegram API failure;
- duplicate Telegram update;
- database failure.

Не проектируй избыточную fault-tolerant distributed architecture.

#### Time handling

UTC storage + Europe/Moscow business timezone + injected/frozen clock.

#### Security

Кратко:

- secrets;
- prompt injection;
- PII redaction;
- XSS;
- CSRF;
- operator authorization.

#### Out of scope

Чётко перечисли сознательно исключённые функции.
