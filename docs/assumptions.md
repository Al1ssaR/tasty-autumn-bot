# Допущения MVP «Вкусная осень»

Этот документ фиксирует только решения, которые не определены однозначно в `docs/task.md` и правилах акции. Он не изменяет бизнес-правила из `docs/promo-rules.md` и не заменяет исходное техническое задание.

## 1. Получение сообщений Telegram через long polling

**Что не определено:** техническое задание требует Telegram-бота, но не задаёт способ получения обновлений и не требует публичного окружения с HTTPS.

**Решение:** локальный MVP использует long polling. Процесс Telegram bot worker запускается вместе с остальными сервисами через `docker compose up`.

**Почему это разумно для MVP:** проверяющему не нужны публичный домен, TLS-сертификат, webhook и внешний tunnel. Локальный запуск остаётся воспроизводимым.

**Ограничение:** одновременно должен работать только один polling worker для одного bot token. Решение не описывает горизонтальное масштабирование приёма обновлений.

**Перед production:** выбрать webhook или управляемый polling исходя из среды развёртывания, требований к масштабированию и доступности публичного HTTPS endpoint.

## 2. Только текстовые сообщения Telegram

**Что не определено:** задание описывает вопросы участников, но не задаёт поведение для фотографий, документов, голосовых сообщений, видео, sticker и других типов Telegram-сообщений.

**Решение:** MVP обрабатывает только текст. Неподдерживаемый тип не анализируется LLM и получает нейтральное сообщение о том, что бот принимает текстовые вопросы.

**Почему это разумно для MVP:** обязательные 25 обращений являются текстовыми; поддержка файлов потребовала бы отдельных решений по хранению, OCR, безопасности и срокам удаления.

**Ограничение:** участник не сможет передать фотографию чека или голосовое сообщение через реализованный сценарий поддержки.

**Перед production:** согласовать необходимые типы вложений, ограничения размера, антивирусную проверку, сроки хранения и необходимость OCR/transcription.

## 3. Поведение при уже открытом обращении

**Что не определено:** задание не определяет, создаётся ли новое обращение на каждое последующее сообщение участника и продолжает ли бот автоматически отвечать, пока обращение обрабатывает оператор.

**Решение:** у участника может быть одно открытое обращение. Последующие сообщения добавляются в его историю без нового LLM-вызова и без создания нового обращения. После закрытия следующее сообщение снова проходит обычную классификацию.

**Почему это разумно для MVP:** оператор видит цельный контекст, статистика не завышается, а автоматический ответ не конкурирует с диалогом, уже переданным человеку.

**Ограничение:** новый независимый вопрос того же участника будет ожидать оператора, пока предыдущее обращение открыто.

**Перед production:** уточнить, нужны ли несколько параллельных обращений, явное разделение тем, повторное открытие и возврат к автоматическому режиму внутри операторского диалога.

## 4. Частичный ответ при эскалации

**Что не определено:** составное сообщение может одновременно содержать вопрос, покрытый правилами, и вопрос, требующий персональных данных или отсутствующего правила.

**Решение:** итоговое действие для такого сообщения — `escalate`. Пользователю можно сообщить только достоверную общую информацию из правил, после чего приложение обязательно добавляет собственное уведомление о передаче оператору. Обращение не считается закрытым ботом.

**Почему это разумно для MVP:** участник сразу получает полезную часть ответа, но система не скрывает, что персональная часть осталась нерешённой.

**Ограничение:** требуется явно отделять справочную часть от результата персональной проверки; модель не может заявлять, что такая проверка выполнена.

**Перед production:** согласовать tone of voice и случаи, когда лучше не давать частичный ответ, чтобы не создавать ложных ожиданий.

## 5. Определение `bot resolved`

**Что не определено:** исходное задание не задаёт точную единицу измерения для количества вопросов, самостоятельно обработанных ботом.

**Решение:** `bot resolved` — одно входящее сообщение, для которого получено и провалидировано решение `answer`, а автоматический ответ успешно отправлен в Telegram.

**Почему это разумно для MVP:** метрика отражает фактически доставленные ответы и вычисляется по сохранённым сообщениям и их состоянию доставки.

**Ограничение:** составное сообщение с несколькими вопросами считается одной единицей; корректно сформированный, но не доставленный ответ не входит в метрику.

**Перед production:** согласовать, нужна ли аналитическая единица «намерение/вопрос» вместо сообщения и отдельная метрика ошибок доставки.

## 6. Определение `escalated`

**Что не определено:** задание не уточняет, считать ли каждое переданное сообщение отдельной эскалацией.

**Решение:** `escalated` — количество созданных support tickets. Последующие сообщения в уже открытом обращении не увеличивают показатель.

**Почему это разумно для MVP:** единица измерения соответствует очереди работы операторов и не зависит от числа уточняющих сообщений участника.

**Ограничение:** показатель не отражает объём переписки внутри одного обращения.

**Перед production:** при необходимости добавить отдельно число сообщений, повторных обращений и нагрузку по темам.

## 7. Среднее время первого ответа оператора

**Что не определено:** задание не задаёт начальную и конечную точки расчёта и поведение для обращений без ответа.

**Решение:** метрика считается как среднее значение длительности `support_tickets.first_operator_response_at - support_tickets.created_at` для каждого отвеченного обращения. Tickets без первого ответа не участвуют. Последующие сообщения участника не меняют начало отсчёта. Полученные секунды форматируются как duration без timezone-преобразования.

**Почему это разумно для MVP:** обе временные точки принадлежат системе и могут быть достоверно получены из хранимых данных.

**Ограничение:** метрика фиксирует действие оператора, а не гарантированное получение сообщения участником; ошибка Telegram-доставки учитывается отдельно.

**Перед production:** согласовать SLA-метрики, рабочие часы, процентили, паузы ожидания и требование считать время до успешной доставки.

## 8. Статистика за всё время

**Что не определено:** задание не требует фильтров по датам или отчётных периодов.

**Решение:** MVP показывает all-time статистику без фильтра по периоду.

**Почему это разумно для MVP:** этого достаточно для требуемых трёх показателей и демонстрации корректного расчёта по данным.

**Ограничение:** нельзя сравнивать дни, недели, операторов или отдельные периоды акции.

**Перед production:** определить отчётные периоды, бизнес-календарь, timezone границ отчёта и необходимые разрезы.

## 9. Фиксированное время evaluation-прогона

**Что не определено:** обращения содержат относительный вопрос «когда следующий розыгрыш», но дата запуска проверки заранее неизвестна.

**Решение:** обязательные 25 обращений прогоняются с frozen clock `2026-09-30T12:00:00+03:00`. Production использует текущее время, переданное приложением в timezone `Europe/Moscow`.

**Почему это разумно для MVP:** результат относительных календарных вопросов становится воспроизводимым и не зависит от дня проверки проекта.

**Ограничение:** evaluation показывает поведение на одном фиксированном временном срезе и не заменяет тесты граничных дат.

**Перед production:** покрыть тестами моменты до и после розыгрыша, окончание регистрации и переход между еженедельным и главным розыгрышами.

## 10. Отсутствие интеграции с сайтом акции

**Что не определено:** не предоставлены API, схема данных или credentials сайта акции, хотя персональные вопросы требуют сведений о чеках, участниках, выигрышах и доставке.

**Решение:** MVP не интегрируется с сайтом акции. Он создаёт обращение и предоставляет оператору историю переписки; предполагается, что оператор проверяет персональные сведения во внешней системе или по внешнему процессу.

**Почему это разумно для MVP:** это соответствует требованию эскалировать персональные вопросы и не требует выдумывать несуществующий API.

**Ограничение:** оператор не сможет проверить статус чека или доставки непосредственно в создаваемой панели.

**Перед production:** определить систему — источник бизнес-данных, способ идентификации участника, API-контракты, права доступа, аудит и обработку ошибок интеграции.

## 11. Простая авторизация операторов

**Что не определено:** задание требует веб-панель, но не описывает identity provider, роли и жизненный цикл учётных записей.

**Решение:** MVP использует обычную session-based авторизацию Laravel и одну операторскую роль. Очередь общая, assignment и сложный RBAC отсутствуют. Первый активный пользователь создаётся локальной интерактивной командой `php artisan operator:create`; публичной регистрации и default credentials нет. `is_active=false` запрещает вход и завершает существующую сессию на следующем защищённом запросе.

**Почему это разумно для MVP:** панель не остаётся публичной, при этом не вводятся SSO и административный контур, которых нет в требованиях.

**Ограничение:** нет UI управления пользователями, самостоятельного восстановления пароля, детальной модели полномочий, команд, смен и автоматического назначения обращений.

**Перед production:** согласовать SSO/MFA, роли, provisioning/deprovisioning, аудит действий и правила доступа к персональным данным.

## 12. Нет автоматической retention policy для support history

**Что не определено:** п. 11.1 правил задаёт срок хранения данных, предоставленных при регистрации на Сайте, но явно не определяет срок хранения сообщений Telegram и операторских обращений.

**Решение:** MVP хранит историю поддержки без автоматического удаления. Это не трактуется как изменение срока хранения регистрационных данных сайта.

**Почему это разумно для MVP:** удаление невозможно корректно реализовать без согласованных правовых оснований, сроков, исключений и требований к аудиту.

**Ограничение:** решение не готово для production с точки зрения полного жизненного цикла персональных данных.

**Перед production:** согласовать категории данных, сроки хранения, legal hold, удаление/анонимизацию, резервные копии и обработку запросов субъектов данных.

## 13. Представление ответа оператора и уведомление о закрытии

**Что не определено:** Telegram показывает все исходящие сообщения от имени одного бота, а исходное задание не задаёт визуальное отличие ответа человека и не описывает уведомление участника при закрытии.

**Решение:** при Telegram-доставке operator message получает prefix `Оператор:`, при этом `messages.body` хранит только исходный текст. Закрытие создаёт application-owned system message с коротким уведомлением. Ticket и pending message сохраняются в одной транзакции, а внешний вызов выполняется после commit; повторное закрытие ничего не создаёт и не отправляет.

**Почему это разумно для MVP:** участник явно видит переход к человеку и завершение обращения, а история сохраняет оригинальный ответ и достоверный delivery state.

**Ограничение:** prefix не содержит имени сотрудника, а failed notification не повторяется автоматически.

**Перед production:** согласовать tone of voice, политику повторной доставки и необходимость отображать оператору отдельный статус уведомления о закрытии.
